# Ship Nota small, download Hohe once

Nota should not bake its speech models into the app binary or move transcription to a server. It should ship a small app, keep Hohe running on the phone, and download the 840 MB model pair once, inside the app, from a host Nota controls. That host should be Cloudflare R2 behind a custom domain, mirrored on Hugging Face. The download needs a size prompt, resumable and hash-checked transfers, a Wi-Fi default, a memory check before the app offers it, and a manifest that versions the models separately from app releases. Literal bundling fails on Google Play, where the 723 MB Hohe file is larger than the 500 MB base-module limit. On the App Store it is allowed, but it charges every installer 840 MB, including people whose phones cannot run the model. Store-hosted packs (Play Asset Delivery and Apple-hosted Background Assets) are free and worth adding later, but they reach only store installs, and Nota has none yet. Ethiopia has no App Store storefront, about 94% of Ethiopian phone web traffic is Android, and in 2026 Apple's packs repeatedly failed in App Review and failed outright on 6% of devices in one large deployment. A transcription server would cost $100–600 a month before the first user. It would stop working during Ethiopia's regional internet shutdowns, put voice recordings under the local-storage rules of Ethiopia's data protection law, and end the promise that notes stay on the phone. Comparable apps point the same way: almost every third-party app with a model of 0.5 GB or more ships small and downloads it from Hugging Face. Aiko is the main exception and bundles. Nota is most of the way there already. Its phone app has a resuming, SHA-256-checking downloader that only lacks a URL, so the remaining work is hosting, background transfer, the manifest and device gating, not a new architecture.

## Baking 840 MB into the binary fails on Play and makes every installer pay

Bundling fails on Android before any design question comes up. Google Play applies its limits to the compressed download: **500 MB for the base module**, 1.5 GB per asset pack, and 4 GB for everything delivered at install ([Play Console Help](https://support.google.com/googleplay/android-developer/answer/9859372)). Compression doesn't help. Nota's own measurements show that **quantized weights compress by only 5–7%** ([docs/embedded-speech.md](../docs/embedded-speech.md)), so the download is about the size of the file. A model declared as an ordinary Flutter asset goes into the base module and exceeds the limit. Flutter's deferred components don't get around this either: they are dynamic feature modules, which have the same 500 MB cap, and Flutter's docs don't mention asset packs ([Flutter docs](https://docs.flutter.dev/perf/deferred-components)). The only way to bundle Hohe in a Play install is an install-time asset pack. That pack counts toward the size shown in the store and needs **at least twice its size in free space** at install time, about 1.7 GB for Nota. It is also read through Android's AssetManager, not as a plain file ([Play Asset Delivery](https://developer.android.com/guide/playcore/asset-delivery)), so ONNX Runtime would probably need the 723 MB copied out to a file, keeping two copies on the phone. Play also warns users on mobile data before any install over 200 MB, though the warning doesn't block the install ([Play Console Help](https://support.google.com/googleplay/android-developer/answer/9859372)).

iOS does allow bundling. The uncompressed app limit is 4 GB, and the 500 MB limit applies only to the executable's code, not to resource files ([Apple](https://developer.apple.com/help/app-store-connect/reference/maximum-build-file-sizes)). Aiko ships its Whisper models inside a **1.8 GB iPhone app** ([Aiko](https://sindresorhus.com/aiko)). Updates are cheaper than people fear. Apple's update package contains only the files whose content changed ([Apple](https://developer.apple.com/documentation/xcode/doing-advanced-optimization-to-further-reduce-your-app-s-size#Reduce-the-size-of-app-updates)), so an update that changes only Dart code would not send Hohe again, as long as the model file stays byte-identical. One 2025 developer report is worth knowing about. A 2.2 GB app's code-only updates finished in 30 seconds over mobile data, but an update that changed resources fell back to a full 2.4 GB download ([Apple Developer Forums](https://developer.apple.com/forums/thread/777442)). The mobile-data rules are less settled than they are usually described. Apple's iOS 17 and 18 guides document an option to be asked before App Store downloads over 200 MB ([iPhone User Guide, iOS 18](https://support.apple.com/guide/iphone/manage-purchases-settings-and-restrictions-iph3dfd91de/18.0/ios/18.0)). Only 2019 third-party articles say that option is the default ([9to5Mac](https://9to5mac.com/2019/06/03/ios-13-removes-200-mb-file-size-limit-for-app-downloads-over-cellular/amp/)), and the iOS 26 guide no longer names a threshold at all ([iPhone User Guide, iOS 26](https://support.apple.com/guide/iphone/change-settings-and-restrictions-iph3dfd91de/26.0/ios/26.0)).

So the case against bundling is about who pays, not about what the stores allow. A bundled model costs every installer 840 MB before they have seen the app. At Safaricom Ethiopia's prices after its December 2025 increase of **up to 82%**, that is roughly **38–50 birr** ([Addis Insight](https://addisinsight.net/2025/12/24/safaricom-ethiopia-raises-data-package-prices-by-up-to-82/)). It also charges users whose phones are too small to run the model (see the memory section below). Bundling can't be targeted either. App thinning makes variants per device, not per iOS version, so bundling the model as a fallback for older iPhones would put it in every iPhone's download. That is an inference; no Apple source states it. Each model change also ships as an app update of about 723 MB, because re-quantizing changes nearly every byte of the weights. Bundling is right only for small models. The speech toolkits that bundle, such as Vosk, whose small models are about 50 MB ([Vosk](https://alphacephei.com/vosk/models)), Picovoice ([Picovoice](https://picovoice.ai/docs/quick-start/leopard-android/)) and the sherpa-onnx demos ([sherpa-onnx](https://k2-fsa.github.io/sherpa/onnx/android/build-sherpa-onnx.html)), all ship models well under 150 MB. Toolkits built around models of 0.5 GB and up download them instead. Getting Nota into the bundling range would take a distilled student of about 95M parameters, roughly 100 MB at 8-bit. The smaller Amharic models that exist are licensed for non-commercial use only and are much less accurate: Ethio-ASR 94M is CC BY-NC-SA 4.0 and scores **30.95 WER** on WAXAL Amharic, against 22.37 for the 600M class ([Ethio-ASR 94M](https://huggingface.co/badrex/Ethio-ASR-multilingual-94M); [Ethio-ASR Amharic](https://huggingface.co/badrex/Ethio-ASR-amharic)). Even 4-bit Hohe comes to about 545 MB with the punctuation model ([docs/embedded-speech.md](../docs/embedded-speech.md)).

## Store-hosted packs are free and promising but reach only store installs

The stores now host large files for free and deliver them after install, which comes closest to the model "just being there". The two platforms differ in maturity, in when updates can ship, and in which users they reach.

| Option | Holds the 723 MB file? | Counted in store size? | Model update without app release? | State in November 2026 |
|---|---|---|---|---|
| Play install-time asset pack or AI pack | Yes (1.5 GB per pack) | Yes | No | Stable; needs 2× free space; read through AssetManager |
| Play fast-follow or on-demand asset pack | Yes | No | No, but delta-patched | Stable library 2.3.0; no official Flutter support |
| Play AI pack (fast-follow or on-demand) | Yes | No | No | Beta; alpha client library 0.1.1-alpha01; adds RAM targeting |
| iOS: model bundled in the app | Yes (4 GB limit) | Yes | No | Simple; every installer pays |
| iOS On-Demand Resources | Only on iOS 18+ (512 MB per pack before) | Unclear | No | Deprecated from iOS 27 |
| iOS Apple-hosted Background Assets | Yes (no per-pack cap published) | Essential packs yes; prefetch and on-demand no | Yes, after App Review | iOS 26+ only; review and download failures throughout 2026 |

Sources: [Play Asset Delivery](https://developer.android.com/guide/playcore/asset-delivery); [Integrate asset delivery](https://developer.android.com/guide/playcore/asset-delivery/integrate-java); [Play for On-device AI](https://developer.android.com/google/play/on-device-ai); [Apple ODR limits](https://developer.apple.com/help/app-store-connect/reference/on-demand-resources-size-limits/); [WWDC25 session 325](https://developer.apple.com/videos/play/wwdc2025/325/); [Apple-hosted asset pack limits](https://developer.apple.com/help/app-store-connect/reference/app-uploads/apple-hosted-asset-pack-size-limits).

On Android, a **plain fast-follow asset pack** is the strongest store-native option. Play downloads it automatically right after install. It doesn't count toward the store size, and it lands as an ordinary file in the app's internal storage with a real path, which suits flutter_onnxruntime's file-based session loading. Over 200 MB on mobile data, the download waits for Wi-Fi or for the user's consent, which the app can ask for with `showConfirmationDialog()`. Apps must state the size before fetching a pack ([Integrate asset delivery](https://developer.android.com/guide/playcore/asset-delivery/integrate-java)). The catch for the update cycle is that **packs update only with app releases**. Small updates are likely but only half documented. The beta AI-packs page says outright that an unchanged pack is not downloaded again ([Play for On-device AI](https://developer.android.com/google/play/on-device-ai)). The plain PAD page describes patches applied locally to the files already on the device, and warns that patching depends on those files staying intact, which only makes sense for a delta update ([Play Asset Delivery](https://developer.android.com/guide/playcore/asset-delivery)). Google's GWENT case study reports **update sizes cut by 90%** with PAD ([CD Projekt RED story](https://developer.android.com/stories/games/cdpr)). Flutter has no official PAD support. The only plugin that covers both stores, `store_asset_packs` 0.1.0, appeared in late October 2026 with 416 downloads ([pub.dev](https://pub.dev/packages/store_asset_packs)). A thin platform channel to Play's `AssetPackManager` is the safer route. AI packs add targeting by RAM, but devices outside every group still receive the default variant, and the feature is still beta with an alpha client library. Plain PAD gives the same delivery at lower risk.

On iOS the store path is shakier. On-Demand Resources are deprecated from iOS 27, and before iOS 18 they cap packs at 512 MB, below Hohe's size ([Apple](https://developer.apple.com/help/app-store-connect/reference/on-demand-resources-size-limits/)). Their successor, **Apple-hosted Background Assets**, looks right on paper. Apple includes 200 GB of hosting with the developer membership. Packs can download as part of the install or afterwards. Pack versions are reviewed and released separately from app builds, and every installed app version switches to the new pack ([WWDC25 session 325](https://developer.apple.com/videos/play/wwdc2025/325/)). In practice the 2026 record is poor. An Apple Frameworks Engineer wrote on Apple's forum (not in any documentation) that **App Review runs with pre-launch downloads turned off**, so the reviewer sees the app's own download screen, which must show the size under Guideline 4.2.3(ii) ([Apple Developer Forums](https://developer.apple.com/forums/thread/815174)). From February to September 2026, several developers reported that the review environment couldn't reach Apple-hosted packs at all. Apple's latest reply, in September, said it was still looking into the problem ([Apple Developer Forums](https://developer.apple.com/forums/thread/843872)). A production app with about 955 MB of packs, close to Nota's payload, reported on 7,384 devices: **68% completed, 6% failed in ways retries didn't fix, and about 25% never finished**. On 178 devices the system reported the pack downloaded while its files were missing, and the developer shipped a hotfix that bundled the content again ([Apple Developer Forums](https://developer.apple.com/forums/thread/845723)). Apple's own documentation warns that even an essential pack can fail to arrive ([Apple](https://developer.apple.com/documentation/backgroundassets/downloading-apple-hosted-asset-packs)). Whatever store mechanism Nota uses, it still needs its own download screen. Apple-hosted packs can only ever be one source behind that screen.

Reach matters most for Nota. **Apple lists no App Store storefront for Ethiopia** ([Apple Support](https://support.apple.com/en-us/118205)). Google Play lets Ethiopian users download free apps ([Google Play](https://play.google.com/supported-locations?hl=en)). In October 2026, Android had **93.8%** of Ethiopian mobile web traffic and iOS 6.0% ([StatCounter](https://gs.statcounter.com/os-market-share/mobile/ethiopia)). Among Ethiopian iPhones, about 69% of web traffic came from iOS 26 or later, the minimum for Apple-hosted packs. That is about three-quarters of the iOS 16+ devices Nota supports today ([StatCounter](https://gs.statcounter.com/ios-version-market-share/mobile/ethiopia)). Nota also isn't in either store. Its release APKs are still signed with the debug key, and its iOS builds are installed from Xcode ([mobile/README.md](../mobile/README.md)). An APK passed between phones over Telegram or SHAREit carries the base app, not Play's packs (an inference; not verified). Store packs therefore make sense as an extra source for store installs, added on top of a download Nota hosts itself, not as a replacement for it.

## Comparable apps ship small and download from Hugging Face

The survey of comparable apps shows a clear split by model size. Apps whose models are 0.5 GB or larger ship a small binary and download the model in the app, usually from Hugging Face. Toolkits with small models bundle them. Apple and Google download per-language packs through the operating system.

Hugging Face is the default host for independent apps, and **none of the surveyed apps documents running its own model CDN**. Aiko is the one clear bundler at Nota's scale. Its developer explains the choice by the cost of building downloadable models, which he calls a large amount of work ([Aiko](https://sindresorhus.com/aiko)). Nota has largely paid that cost already. Two hybrids are worth copying. Whisper Notes bundles a default model and offers bigger ones as optional downloads. Private LLM keeps a built-in fallback model and switches to a Hugging Face mirror on networks that block the main site, and its FAQ suggests a hotspot or VPN when Hugging Face is unreachable ([Private LLM FAQ](https://privatellm.app/en/faq)). That is a direct warning for Nota: a download from Hugging Face alone has no fallback if Ethiopian networks throttle or block it. Apps that download models also restrict on-device models to the iPhone 15 and later, which suggests **memory, not storage, is the binding limit** for models of 0.5–1.5 GB. The most common user complaints are downloads stuck partway, downloads that restart from zero, and models downloaded again that should have been cached ([LLM Farm on the App Store](https://apps.apple.com/gb/app/llm-farm/id6461209867)). Resume support and caching are therefore baseline requirements, not polish.

Two gaps in the survey matter for Nota. No surveyed consumer app documents using Play AI packs or Apple-hosted Background Assets, so Nota would be an early adopter of either. And Nota can't rely on the platform recognizers: a Flutter package that wraps them reports that iOS doesn't support Amharic recognition, and that offline Amharic on Android needs a language pack most devices lack ([amharic_stt](https://pub.dev/documentation/amharic_stt/latest/)). The search found no shipping app that does offline Amharic speech recognition with its own model, so Nota has no direct precedent to follow.

## A self-hosted download costs nothing and keeps notes on the phone

### Free egress is available if Hohe is split into parts

At Nota's likely volumes, bandwidth is the only cost that matters. Storing two model versions and paying request fees cost almost nothing on every host. The table below prices 840.6 MB per full download at Africa and Middle East rates where they differ.

| Host | 1,000 downloads/month | 10,000/month | 100,000/month | Catch |
|---|---|---|---|---|
| Cloudflare R2, custom domain | ~$0 | ~$0 | ~$0 | Files over 512 MB aren't edge-cached on non-Enterprise plans |
| Hugging Face Hub | $0 | $0 | $0 | Best-effort storage; 3,000 anonymous downloads per 5 min per IP |
| GitHub Releases | $0 | $0 | $0 | 2 GiB per file; acceptable-use clause on excessive bandwidth |
| CloudFront flat-rate Pro | $15 | $15 | Over the 50 TB allowance | 50 TB ≈ 59,000 downloads |
| CloudFront pay-as-you-go | $0 | ≈ $815 | ≈ $8,255 | Metered |
| Bunny Standard (Middle East and Africa) | ≈ $50 | ≈ $504 | ≈ $5,044 | Metered |
| Backblaze B2, direct | ≈ $8 | ≈ $84 | ≈ $840 | No CDN |

Sources: [R2 pricing](https://developers.cloudflare.com/r2/pricing/); [Cloudflare cache limits](https://developers.cloudflare.com/cache/concepts/default-cache-behavior/); [HF rate limits](https://huggingface.co/docs/hub/rate-limits); [GitHub releases](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases); [GitHub acceptable use](https://docs.github.com/en/site-policy/acceptable-use-policies/github-acceptable-use-policies); [CloudFront](https://aws.amazon.com/cloudfront/pricing/); [CloudFront pay-as-you-go](https://aws.amazon.com/cloudfront/pricing/pay-as-you-go/); [Bunny](https://bunny.net/pricing/cdn/); [Backblaze](https://www.backblaze.com/cloud-storage/pricing).

**Cloudflare R2 is the best host Nota can control itself.** It charges nothing for egress ([R2 pricing](https://developers.cloudflare.com/r2/pricing/)), and Cloudflare lists a point of presence in **Addis Ababa** ([Cloudflare network](https://www.cloudflare.com/network/)). The public `r2.dev` address is rate-limited and meant for development, so Nota needs a custom domain on Cloudflare ([R2 public buckets](https://developers.cloudflare.com/r2/buckets/public-buckets/)). The caching limit also matters: Free, Pro and Business plans cache files of at most 512 MB ([Cloudflare](https://developers.cloudflare.com/cache/concepts/default-cache-behavior/)). Splitting hohe-w8.onnx into parts of about 100–360 MB lets the edge cache serve them. It also makes each retry smaller on a poor connection. The app joins the parts and checks the whole-file hash. Hugging Face should be the second source in the manifest. It costs nothing and serves through CloudFront, and its responses carry byte-range support and SHA-256 headers. But its free storage is best-effort and its per-IP rate limits are subject to change ([HF storage limits](https://huggingface.co/docs/hub/storage-limits); [HF rate limits](https://huggingface.co/docs/hub/rate-limits)). Mobile carriers that put many users behind one IP address could hit those limits; the notes found no data on Ethiopian carriers. Download time depends mostly on the user's own connection. 840 MB takes about **11 minutes at 10 Mbps and nearly 2 hours at 1 Mbps**, so the download has to survive interruptions.

Self-hosting doesn't conflict with the privacy promise or the licences. The download sends no user data beyond an IP address and a user agent. Apple doesn't require disclosure of an IP address that is sent with a request and not kept, and it counts on-device processing as not collected. Google counts data as collected only when user data leaves the device ([Apple privacy details](https://developer.apple.com/app-store/app-privacy-details/); [Google Play Data safety](https://support.google.com/googleplay/android-developer/answer/10787469)). Nota's privacy policy should still say that the model comes from a CDN, and Nota should keep its own access logs briefly or not at all. Both licences allow hosting copies. CC BY 4.0 requires credit, a licence link, and a note that the material was modified ([CC BY 4.0](https://creativecommons.org/licenses/by/4.0/legalcode.en)); "converted to ONNX and quantized to 8-bit" covers the modification. Apache-2.0 requires the licence text and the upstream notices ([Apache-2.0](https://www.apache.org/licenses/LICENSE-2.0)). The desktop build already writes a NOTICE that names both models ([scripts/build_speech_models.py](../scripts/build_speech_models.py)). Nota can host it next to the files and show it in the app.

### Nota's existing downloader needs background transfer, not a rewrite

The phone app already does much of what the comparable apps do. `ModelStore` downloads each file to a `.part` file and resumes with an HTTP Range request. It checks the size and then the SHA-256 in a background isolate, renames the file into place only after it matches, and deletes a mismatched part. It also imports files picked from the phone ([model_store.dart](../mobile/lib/features/speech/models/model_store.dart)). The expected sizes and hashes are compiled into the app ([model_files.dart](../mobile/lib/features/speech/hohe/model_files.dart)), so the trust anchor sits in the store-signed binary. The download URL is a build-time setting left empty because "nothing is hosted yet" ([mobile/README.md](../mobile/README.md)). Three things are missing. The download runs only while the app is open in the foreground. It resumes without an If-Range check against the server's ETag. And it has no retry policy, Wi-Fi rule or fallback host. background_downloader 9.6.6 covers most of this ([pub.dev](https://pub.dev/packages/background_downloader)). On Android 14+, its user-initiated hint runs the transfer as a user-initiated data transfer job, which removes WorkManager's 9-minute limit; Android 7–13 needs its foreground-service option instead ([parameters](https://github.com/781flyingdutchman/background_downloader/blob/main/doc/parameters.md); [Android UIDT](https://developer.android.com/develop/background-work/background-tasks/uidt)). Nota should also turn off its cache-directory option, check free space before starting, lengthen the iOS transfer timeout well past its 4-hour default, and add a Wi-Fi-only toggle with a "use mobile data anyway" override. iOS cancels background transfers when the user force-quits the app and doesn't relaunch it ([Apple](https://developer.apple.com/documentation/foundation/urlsessionconfiguration/background(withidentifier:))). Resuming on the next launch must therefore be a normal path, built on the `.part` logic Nota already has. PocketPal's Android engine is a good reference for the edge cases ([DownloadEngine.kt](https://github.com/a-ghorbani/pocketpal-ai/blob/main/android/app/src/main/java/com/pocketpalai/download/DownloadEngine.kt)). It resumes only when the server's ETag is strong and unchanged, treats a 416 response with a complete file as done, and retries 408, 429 and 5xx errors with backoff.

### Model releases can run on their own track, and should be rare

The update cycle is the main thing self-hosting gives Nota beyond what PAD offers. A small remote manifest lists each model's version, a format number the app understands, a minimum app version, file sizes, hashes and two URLs. The desktop build's `models/manifest.json` already records the bytes, SHA-256, upstream revision and toolchain for each file, so it is the natural starting point. The app picks the newest model whose format it supports. It downloads the new version into a staging folder in the background and keeps the old one until the new one passes its hash check, loads in ONNX Runtime, and transcribes a bundled one-second clip to a known string. Then it switches over and deletes the old version. Hohe (723 MB) and punctuation (117 MB) should be versioned separately, so a punctuation fix never triggers an 840 MB download. Updates should default to Wi-Fi only. Once hashes move out of the binary, the manifest should be signed with a key embedded in the app, so a tampered file on R2 or Hugging Face is rejected. This signing step is this report's own design recommendation; no source in the research covers it. Apple's developer support has said that updating ML models after install **"isn't in conflict with App Store guidelines"** and noted that existing apps rely on it, while advising developers to confirm with App Review ([Apple Developer Forums](https://developer.apple.com/forums/thread/793131)). Swapping in a better Hohe for the same feature is the safe case. A downloaded model that adds a new capability, such as another language, is a grey area under Guideline 2.5.2, which bars downloaded code that changes an app's features ([App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/)). Play bans downloading executable code such as dex, JAR and .so files, and ONNX weights are none of those ([Play policy](https://support.google.com/googleplay/android-developer/answer/9888379)).

In practice, model updates will be infrequent and expensive. The upstream Hohe repository has eight commits, all made between 20 September and 5 October 2026 ([HF commits](https://huggingface.co/api/models/snapwre/hohe-asr-amharic/commits/main)). After any re-quantization, nearly every weight byte changes, so binary diffs save little and an update costs close to the full 723 MB. Nota should freeze the model files' bytes, checked by hash in CI, and treat a model release as a deliberate, rare event. With a separate release track, those rare updates no longer have to wait for an app release or an app review: a model fix reaches every installed version that understands its format.

### Memory, not bandwidth, decides who should download

Before offering an 840 MB download, Nota should check whether the phone can use the model. Transcribing needs about **2 GB of free memory** ([mobile/README.md](../mobile/README.md)). Loaded and idle, the 8-bit model takes about 0.9 GB. On the desktop, peak memory was 1.8 GB on 11-second clips and 2.9 GB on 27-second pieces ([docs/embedded-speech.md](../docs/embedded-speech.md)), which puts the phone's 20-second pieces at roughly 2.3–2.5 GB by interpolation. No public source gives a breakdown of Ethiopian phones by RAM. The proxies suggest 4 GB is the norm: current budget Tecno models listed in Ethiopia ship with 4 GB ([Jiji](https://jiji.com.et/mobile-phones/tecno-spark-30c)), and about 16% of Ethiopian Android traffic still comes from Android 11–12 ([StatCounter](https://gs.statcounter.com/android-version-market-share/mobile-tablet/ethiopia)). The 2026 memory price spike, which pushed memory past 64% of the bill of materials for phones under $99, will keep low-RAM phones in use longer ([Ecofin Agency](https://www.ecofinagency.com/news/1509-58915-africas-40-smartphone-ambition-runs-into-memory-prices-and-customs-costs)). On many 4 GB phones, the 8-bit model at 20-second pieces will probably run out of memory. A **4-bit Hohe** is the candidate for those phones. It is 427 MB and uses 0.6 GB idle. It matches 8-bit on clean FLEURS speech, adds about 0.5 CER points on conversational speech, and changes 4–8% of the text on Nota's own recordings, which no one has yet hand-checked ([docs/embedded-speech.md](../docs/embedded-speech.md)). The manifest can list both variants with a minimum-RAM field, which gives Nota the same targeting as Play's AI packs without the beta. The app can read Android's total memory and low-RAM flag, and on iOS call `os_proc_available_memory` and request the increased-memory-limit entitlement ([Apple](https://developer.apple.com/tutorials/data/documentation/bundleresources/entitlements/com.apple.developer.kernel.increased-memory-limit.md)). Before choosing, test both models on a real 4 GB phone. Once Nota is on Play, Play Console's device statistics will give the actual RAM breakdown, gathered by Google without breaking the on-device promise.

## Server transcription fails where Amharic speakers need it most

A server looks cheap per minute of audio but expensive in every other way. If the machines stay busy, compute costs a few cents per audio hour. An 8-vCPU endpoint is $0.268/h and an L4 GPU $0.80/h on Hugging Face ([HF Inference Endpoints](https://huggingface.co/docs/inference-endpoints/pricing)), and RunPod offers L4 pods from $0.44/h ([RunPod](https://www.runpod.io/pricing)). But avoiding cold starts means keeping at least one machine running: **about $98 a month for a 4-vCPU endpoint and $430–584 for an L4**, before the first user. The research's scenarios put 100,000 users at roughly **$2,400 to $105,000 a month**, depending on how much they record and on throughput figures for Hohe on server hardware that no one has measured. Cheap hosted speech APIs don't help. Cloudflare's Whisper costs $0.0005 per audio minute ([Workers AI pricing](https://developers.cloudflare.com/workers-ai/platform/pricing/)), but stock Whisper is unusable on Amharic: the project measured about 193% CER ([CLAUDE.md](../CLAUDE.md)), and an independent benchmark recorded 164.1 WER on FLEURS ([WAXAL-NET](https://arxiv.org/html/2606.02375)). On the protocol question, Hohe is a full-context CTC model, not a streaming one, and Nota already cuts dictation into clips at pauses. A REST call per clip fits how the model works. A WebSocket saves connection setup but doesn't produce word-by-word results, and sherpa-onnx's ready-made servers don't cover Hohe's feature front end ([sherpa-onnx](https://k2-fsa.github.io/sherpa/onnx/websocket/online-websocket.html)).

On data use, a server only wins if the audio is compressed. Opus at 16 kbit/s, the recommended rate for wideband speech ([RFC 6716](https://www.rfc-editor.org/rfc/rfc6716)), uses about 7.2 MB per hour. A user would need about **117 hours of transcription** before uploads cost more data than the one-time 840 MB download. With uncompressed 16 kHz WAV, the break-even comes after about 7 hours. No GPU cloud region could be confirmed in Ethiopia. A 2022 measurement found a median of 84 ms from African probes to the AWS Africa region ([AFPIF 2022](https://www.afpif.org/wp-content/uploads/2022/09/2-Cloud-Latency-in-Africa-JosiahChavula-Kigali-August2022.pdf)), which is tolerable for clip-by-clip dictation when the network works.

The network often doesn't work. Mobile and fixed internet in **Amhara**, a core Amharic-speaking region, was cut on 3 August 2023 after fighting escalated ([Access Now](https://www.accessnow.org/press-release/amhara-internet-shutdown/)). Tigray's 2020–2022 blackout was called the world's longest uninterrupted shutdown ([Access Now](https://www.accessnow.org/tigray-internet-shutdowns/)). In September 2026, NetBlocks detected a new disruption in northern Ethiopia as war resumed ([TimesLive](https://www.timeslive.co.za/news/africa/2026-09-25-internet-disruption-detected-in-war-hit-northern-ethiopia-web-monitor-says/)). A server-dependent dictation feature would stop working for these users, sometimes for months. The same shutdowns block the first model download, which is why Nota should keep its file import: a model copied from another phone or a computer works during a shutdown.

Privacy and law add a third barrier. Sending voice to a server counts as collecting Audio Data under Apple's rules, unless the server discards it immediately after the request ([Apple privacy details](https://developer.apple.com/app-store/app-privacy-details/)). Google treats it as collecting "Voice or sound recordings" ([Google Play Data safety](https://support.google.com/googleplay/android-developer/answer/10787469)). It would also force Nota to rewrite the "notes stay on this phone" promise. Ethiopia's Personal Data Protection Proclamation No. 1321/2024, in an unofficial English text, requires personal data collected in Ethiopia to be stored on servers in Ethiopia (Art. 22(1)). It requires the Authority's prior approval to send sensitive data abroad (Art. 22(3)), and registration before any processing (Art. 33) ([Proclamation 1321/2024](https://www.metaappz.com/References/ethiopian_laws/federal/pr_1321_2024/en/txt)). Whether transient transcription counts as storage is a question for an Ethiopian lawyer. The platforms do run hybrids: Android's recognizer streams audio to servers by default and offers an on-device mode with model downloads ([Android SpeechRecognizer](https://developer.android.com/reference/android/speech/SpeechRecognizer)). For Nota the right hybrid is the reverse of theirs: on-device by default, with a server only as an opt-in, clearly labelled extra for phones that can't run any Hohe variant.

## Recommendation: download first, add store packs later, keep any server optional

The first phase should finish what the phone app has started. Host the 4-bit and 8-bit Hohe files (split into parts of 512 MB or less) and the punctuation model on R2 behind a Nota domain, with a Hugging Face mirror. Publish a signed manifest with per-model versions, format numbers and minimum-RAM fields. Move the existing downloader onto background transfers with If-Range resume, retries, a Wi-Fi default and a free-space check. Gate the offer by memory, and keep the file import. The first-run screen should show the size, the estimated time and a Wi-Fi recommendation before anything downloads, as Guideline 4.2.3(ii) requires ([App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/)). Notes, tags and search should work without the model. Review notes should explain the download and attach an Amharic sample the reviewer can import, because the current copy-it-in flow would leave a reviewer unable to reach the speech feature. Distribution needs a release keystore whichever channel Nota picks. Google's developer verification extends to apps installed outside Play on certified devices in 2027, after which an unregistered APK installs only after a one-time advanced flow with a day's wait ([Android developer verification FAQ](https://developer.android.com/developer-verification/guides/faq)).

The second phase adds store delivery where Nota has store installs. Once Nota is on Play, a fast-follow asset pack, reached through a thin platform channel, becomes the first source for Play installs, behind the same screen and the same hash check. Its update cost should be measured on an internal test track before relying on it. Apple-hosted packs belong in a third phase, as an optional source for iOS 26+ installs, and only after the review-environment and missing-file reports are resolved. A transcription server comes last, as an opt-in, if any. The table below shows what would move each part of this plan.

| If this turns out true | Then change the plan this way |
|---|---|
| Most Android users install from Play | Make the PAD fast-follow pack the main Android path; keep the self-hosted download for APK users and as a fallback |
| Apple fixes the App Review access and missing-file problems, and Nota raises its iOS minimum to 26 | Use Apple-hosted packs as the main iOS source, with independent pack versions |
| A distilled Amharic model under ~150 MB reaches acceptable CER | Bundle it in the binary on both stores and drop the download for the default model |
| Device tests show most target phones can't run even 4-bit Hohe | Build an opt-in, Ethiopia-hosted server path with consent screens and new privacy labels |
| Hugging Face or Cloudflare is blocked or throttled on Ethiopian networks | Add another mirror (Bunny's Nairobi PoP, or GitHub Releases) to the manifest |
| Models start changing monthly | Invest in the signed manifest and staged rollouts; this strengthens the case for self-hosting over PAD, which ties model updates to app releases |

## Conclusion

The question looked like "where should 840 MB live?", but bandwidth turned out to be the smallest of the constraints. Hosting is free at any plausible volume, and the download costs a user about as much as a few hours of browsing. The decisive factors are distribution channel and memory. Nota's users are overwhelmingly on Android, often outside the stores, sometimes offline for months, and on 4 GB phones that may not run the 8-bit model. Each of those facts favours a download Nota controls, a memory check before it, and a file-import path that works without the internet. Store-hosted packs are an optimization for store installs, not the foundation. Bundling is a real option only if a model under about 150 MB comes along.

The update cycle needs a separate release track more than it needs speed. Hohe upstream changes rarely, and any re-quantized update costs users almost the full 723 MB. The value of a separate track is that a model fix can ship without an app review and without a new binary on every phone. The work to do now is to freeze the model bytes, sign what the app trusts, and treat model releases as rare events with their own version numbers. Nota already pins file hashes in the reviewed binary, so it is well placed to do this.
